# Setting it up

Two deployments off one repo, both reading the same Supabase project.

| | Root directory | Where it lives |
| --- | --- | --- |
| Public site | `apps/web` | Vercel, until `ta-nnin.be` moves |
| Admin | `apps/admin` | Vercel, until `admin.ta-nnin.be` moves |

**Right now this is a demo on Vercel's own URLs**, for Tawat to look at. The
site works that out for itself - canonical tags, the sitemap and the cancel
link in booking emails all point at wherever it is actually deployed, not at a
domain it is not on yet.

It also keeps itself **out of Google** until then. A demo in search results
would be a half-finished version of the bar competing with the real site later,
so anything that is not `ta-nnin.be` serves `Disallow: /` and a `noindex` on
every page.

**Going live is one action, not a code change**: attach `ta-nnin.be` to the
Vercel project as its production domain and redeploy. Vercel then reports it as
the production URL, the site recognises itself, and indexing turns on. There is
no variable to remember.

## 1. The database

Open **`supabase/setup.sql`**, copy all of it, paste it into the Supabase SQL
editor and press run. That is the whole step.

It is the nine migrations and the seed joined together, and **it is safe to run
again**. If you cannot remember whether you have already done this, run it -
that is the right answer rather than a risk. Nothing in it fails on a database
that is already set up, which is checked by a test that pastes it twice into a
real Postgres.

The one thing a re-run overwrites is the menu, the wine list and the bar list:
the seed clears those and re-inserts them from the repo, so anything Tawat has
changed in the admin since the last deploy goes with it. Bookings, staff logins,
the table plan and blackouts are untouched.

| | |
| --- | --- |

Adding a migration means adding a numbered file here and re-running the bundle
script. `npm test` fails if `setup.sql` is out of date, so it cannot be
forgotten.

## 2. The first owner

**Staff sign in with a username** - `tawat`, not an email address. Supabase has
no username mode, so `apps/admin/lib/identity.ts` builds the address underneath:
`tawat` becomes `tawat@staff.ta-nnin.be`, a subdomain we own and never route.
Nobody sees or types it. That file is the only place the rule lives.

Creating an owner through the admin requires already being one, so the first is
made by hand. **Authentication → Users → Add user**, tick *Auto Confirm User*,
and give it:

- **Email:** `tawat@staff.ta-nnin.be` - the synthetic form of the username
- **Password:** from a password manager, not one written down behind the bar

Then in the SQL editor:

```sql
insert into staff (user_id, email, full_name, role)
select id, email, 'Tawat', 'owner'
from auth.users
where email = 'tawat@staff.ta-nnin.be';
```

Everyone else is added from the admin's People page, which takes the username on
its own and does this part for you.

**Keep one owner on a real email address.** An `@` is passed straight through, so
an account created as `you@gmail.com` signs in with that. It is the way back in:
a username has no inbox, which means no forgot-password mail, so resetting a
staff password is an owner's job in **Authentication → Users**. Lose the only
owner password and there is nothing to click.

Sign-in by one-time link still works, but only for an account on a real address -
asking for a link as a username is refused rather than sent nowhere.

## 3. Environment variables

Both apps need the project URL and the anon key, from **Settings → API**. The
anon key is meant to be public - it ships in the browser on every Supabase site,
and row-level security is what actually guards the data.

Public site (`apps/web`):

```
NEXT_PUBLIC_SUPABASE_URL
NEXT_PUBLIC_SUPABASE_ANON_KEY
```

Admin (`apps/admin`) - the same two, plus:

```
SUPABASE_SERVICE_ROLE_KEY
```

**Never give the service-role key a `NEXT_PUBLIC_` prefix.** It bypasses
row-level security completely. It exists only so `/api/staff` can create and
delete logins, which the anon key is not permitted to do, and it must stay on
the server.

If the Supabase–Vercel integration is connected, the two public variables are
injected and kept in sync automatically; only the service-role key needs adding
by hand, to the admin project.

### `THROTTLE_SALT` - set this before launch

On the website project only:

```
THROTTLE_SALT=<any long random string, e.g. openssl rand -hex 32>
```

The site confirms tables by itself, which means a script can take every table in
the diary - and burn the day's Resend allowance on the way past - without a
person ever seeing it. `0009` caps how many bookings one source can make in an
hour, counted against the guest's email and against the caller's IP.

The IP is hashed with this salt before it reaches the database, so no visitor
addresses are stored and there is nothing there to leak or disclose. Leave the
salt unset and bookings still work, but the IP half of the throttle switches off
and only the email half remains - which stops a stuck retry loop and not much
else. It fails that way deliberately: an unsalted hash of an IP is not anonymous,
because the whole IPv4 space can be hashed and looked up in minutes, so storing
one would be no better than storing the address.

Six bookings an hour per source. Nobody booking a table for real will meet it;
if somebody ever does, they are told to ring rather than shown a failure.

### `CRON_SECRET` - recommended, admin project only

```
CRON_SECRET=<any long random string>
```

Guards `/api/cron/reminders` - see **6. Booking reminders** below. Vercel
attaches this automatically as the request's bearer token once it is set, so
there is nothing else to configure. Leave it unset and the route still runs on
its schedule, just without checking who is calling it.

## 4. The table plan

**Check this before taking a real booking.** `0008` and `0010` load the plan as
described from memory - 3×6, 6×4 and 5×2 on the terrace, a long 16 plus 3×4 and
3×2 inside, a high table for 4 across from the bar, and 5 stools at the bar
itself. That is 95 covers, all of them bookable, and a good deal more than the
40 the old capacity guess assumed.

It is provisional until somebody measures the room. Correct it on the admin's
**Tables** screen: every row is a table somebody can sit at, so if it is not
listed the website will never book it, and if it is listed twice it will book it
twice.

One row is deliberately out of the website's reach:

- **The long 16** has a minimum party of 10, and the website will not take a
  booking above 8. It is there for walk-ins and events; taking it for a couple
  would be the worst possible use of it.

**The bar stools are five separate one-seat rows**, not one row of five. That is
what lets a solo guest book a stool without holding the whole bar for the turn -
and because the allocator takes the smallest table that fits, a party of one now
gets a stool instead of a two-top. A pair who want the bar walk in.

`Min` is what stops a couple taking the six-top while four people are turned
away. Leave it at 1 for a table you are happy to seat anyone at.

**The terrace has its own switch.** Fourteen of the tables are outside, and in
Belgium that is a seasonal and frankly hourly question. Closing the terrace on
the Tables screen takes all of them out of the website's reach in one go, rather
than fourteen at a time.

The same screen sets **how long a table is held** - 105 minutes to start with.
Too short and two parties arrive at once; too long and the room books out on
paper while sitting half empty. It is a judgement, not a fact, which is why it
is a button rather than a constant in the code.

## 5. Booking email

Bookings work without this. Requests save and show up in the admin either way -
the confirmation screen just stops promising an email, and the bookings board
says plainly when nothing was sent. So this can wait, but not for long: without
it, somebody has to notice a new request by opening the admin.

Six triggers:

| Trigger | Goes to | Language |
| --- | --- | --- |
| Booked, table free | Guest - "your table is confirmed" | Theirs |
| Booked, nothing fits | Guest - "we have your request" | Theirs |
| Booked, nothing fits | Staff - "a request came in" | English |
| Staff press Confirm | Guest - "your table is booked" | Theirs |
| Staff press Decline | Guest - "we cannot do that time" | Theirs |
| Guest cancels | Staff - "a table freed up" | English |

**One email per booking in the normal case.** A table that confirms itself sends
the guest a confirmation and sends staff nothing - it is already on the board,
and an alert about something needing no decision is what teaches people to stop
reading the alerts.

Seated and no-show send nothing. Emailing somebody to say they did not turn up
is not a thing a wine bar should do.

### Setting it up

1. Make an account at [resend.com](https://resend.com). The free plan covers
   **3,000 emails a month, capped at 100 a day**. The daily cap is the real
   ceiling, and at one email per confirmed booking it is a long way above what
   the room seats.
2. **Add the domain** `ta-nnin.be` and set the DNS records it asks for. This is
   the step people skip: until a domain is verified, Resend only delivers to the
   address that owns the account, so every guest email silently goes nowhere.
   The free plan allows exactly one domain.
3. Create an API key and set `RESEND_API_KEY` on **both** Vercel projects, plus
   `BOOKING_FROM_EMAIL` (an address on the verified domain) and
   `BOOKING_STAFF_EMAIL` on the website project.

### Checking it works

Book a table on the live site using your own address. If a table was free you
should get a confirmation and staff should get nothing. Book a party of seven
with nothing that size free, and you should get "we have your request" while the
staff inbox gets the alert; confirm it in the admin and check the second email
arrives. If the board says *"Saved - but no email was
sent"*, the key is missing on the admin project rather than the website one.

## 6. Booking reminders

Two more emails per confirmed booking: one the day before, one the same
morning. Both go out from a single Vercel Cron job on the **admin** project -
`apps/admin/vercel.json` triggers `/api/cron/reminders` once a day, at 07:00
UTC (roughly 08:00 in Brussels; Vercel cron schedules are fixed to UTC and do
not shift for daylight saving, so this drifts to roughly 09:00 local in
summer).

It runs in admin rather than on the website because reading a guest's name and
email to remind them needs the service-role key, same as everything else in
**3. Environment variables** above.

Only bookings made more than 48 hours before the sitting get reminded - one
made three hours out already has its confirmation and does not need a second
email on top of it. Each booking is reminded at most once per kind: the two
send timestamps live on the row itself, so a booking that already got its
day-before reminder is not sent it again on a redeploy or a retried cron run.

Nothing to configure beyond `CRON_SECRET` above. If Resend is not set up yet,
this fails the same quiet way every other send in this codebase does - logged,
not thrown - so it is safe to leave running while email is still being set up.

## 7. Running it locally

Node 20 or newer.

```bash
npm install
npm run dev
```

Site on `http://localhost:3000`, admin on `http://localhost:3001`.

Copy each app's `.env.example` to `.env.local` first.

## 8. Before the hosted menu can be cancelled

Two things, in this order - getting them the wrong way round leaves the room
without a drinks list:

1. Check Tawat can add a wine, change a price and mark something sold out from
   his phone, on the real admin.
2. Reprint the table cards with a QR pointing at `https://ta-nnin.be/drinks`.
   The current codes encode a one2three token, so they resolve on that vendor's
   servers and die with the account - they cannot be redirected.

Keep the URL fixed forever and that is the last reprint needed.

## 9. Gift vouchers (Stripe)

The voucher Tawat sells over the bar, sold on `/gift` (Dutch `/cadeaubon`) and
taken at the till on the admin's **Vouchers** tile. Until the keys below are
set, `/gift` shows the card and says it is sold at the bar, so this can deploy
before Stripe exists.

**How it works.** The buyer picks a value (presets 50, 100, 150, 250, 500, or any whole amount from 20 to 3000 typed) and
fills in the card's three lines: for, from, a short note. The site stores a
`pending` voucher with no code and sends them to Stripe Checkout. When Stripe
says the money is in - the webhook or the thank-you page, whichever comes
first - the voucher gets a five-digit code (from 10000 up), an expiry 12 months out, and
an A4 PDF voucher (readable on a phone) is emailed to the buyer through the same Brevo SMTP as
bookings. Staff scan the QR on the voucher (or type the code), take
off what was spent, and the rest stays on it. Paper vouchers sold at the bar are
made on the same screen so everything is in one register.

**Setting it up**

1. Tawat creates the Stripe account (Belgium, business details, ID, IBAN) and
   invites Sacha under Settings → Team with the **Developer** role.
2. Settings → Payment methods: Bancontact, cards, Apple Pay, Google Pay on.
3. Run migrations `0053_gift_vouchers.sql` and `0054_gift_voucher_cap.sql` (or the whole `setup.sql`). The owner
   gets the new **Gift vouchers** permission automatically; anyone else who works
   the till gets it ticked on the People screen.
4. On the `tannin-web` Vercel project, add `STRIPE_SECRET_KEY` (Secret),
   `STRIPE_WEBHOOK_SECRET` (Secret) and `ADMIN_URL` - see `apps/web/.env.example`.
   `SUPABASE_SERVICE_ROLE_KEY` is already there. Redeploy.
5. In Stripe → Developers → Webhooks, add `https://<site>/api/stripe/webhook`
   with the four events listed in `.env.example`, and copy its signing secret
   into `STRIPE_WEBHOOK_SECRET`.

Do all of this with test keys first (`sk_test_...`, card `4242 4242 4242 4242`),
buy one, redeem it in the admin, then swap to live keys and a live webhook.

**Refunds** are done in the Stripe dashboard. A full refund cancels the voucher
automatically; a partial one does not (some of it may already be spent), so
cancel or adjust by hand in the admin.

**The design** is the Canva PDF in `packages/voucher/assets/`. To change it,
export a new one with the same layout, replace the file and run
`node scripts/embed-voucher-assets.mjs`.
